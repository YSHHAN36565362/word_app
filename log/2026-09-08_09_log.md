# 2026-09-08 작업 로그

## 1. 여러 기기 진행 기록 보존 + 기기 이름 표시 + 긴 파일명 스크롤

## 요청 사항

"개인 번호 저장을 하면 그 기기에서는 세션을 끄고 전원을 끄고 켜도 잘 저장 되는데,
같은 번호면 다른 기기에서 진행한 것도 다른 기기에서 불러오거나 저장 추가로 하기도
있으면 좋겠는데, 어려울까? 예전에는 잘 되었는데, 어느 순간부터 저장 연동이 안됨.
그리고 저장 덮어씌우기 전에, 마지막 공부 날짜나 접속한 기기(맥북, 데스크탑, 아이폰,
아이패드 등 기기 이름)을 확인하면 좀 더 확실히 어떤 기록을 남겨야 하는 것을 알
듯. 일단 기록을 모두 유지 시켰다가 내가 원하는 것을 지울 수 있게 해줘. 그리고
모바일 연습모드 등에서 첫 화면에서 기록을 볼 때, 선택이 많고 파일 이름이 길면
뒤가 ...으로 다 안보여, 스크롤 기능을 넣어서 모든 내용을 볼 수 있게 해줘."

## 원인 — 스키마 자체가 "기기당 한 슬롯"이 아니라 "조합당 한 슬롯"이었다

`progress`/`learning_log` 테이블은 기본키가 `(user_id, part, file_key)`뿐이었다.
즉 같은 번호로 같은 파일 조합을 다루면 **기기가 달라도 행이 하나뿐**이라, 나중에
저장한 기기가 upsert로 이전 기기의 행을 그대로 덮어썼다 — "전에는 잘 됐는데 어느
순간부터 안 된다"는 것도, 딱 두 기기를 번갈아 쓰기 시작한 시점부터 이 문제가
드러났을 것이다. 이건 진짜 동기화 버그였고, 스키마 차원의 변경 없이는 고칠 수 없는
문제였다(그래서 "어려울까?"라고 물어본 것도 타당했다 — 로컬 사본 병합 로직만으로는
못 고치고 Supabase 테이블 구조를 바꿔야 했다).

## 구현 — device_id를 기본키에 추가

1. **`src/lib/device.ts`(신규)**: 이 브라우저(기기)를 가리키는 `device_id`(한 번
   만들어지면 localStorage에 계속 남음)와, 사용자가 직접 지을 수 있는 `device_label`
   (기기 종류를 User-Agent로 추측해 기본값으로 채워둠 — 맥/윈도우 PC/아이폰/
   아이패드/안드로이드 등)을 관리한다.
2. **`supabase/schema.sql`**: `progress`·`learning_log` 두 테이블에
   `device_id`·`device_label` 컬럼을 추가하고, 기본키를 각각
   `(user_id, part, file_key, device_id)`로 바꿨다. 기존 행은 `device_id=''`
   기본값으로 그대로 남아 "예전 기록(기기 정보 없음)"으로 보이며, 데이터 유실은
   없다. `add column if not exists`/`drop constraint if exists` 패턴이라 이미
   Supabase를 설정해둔 배포에도 파일 전체를 다시 실행하면 안전하게 적용된다
   (README에 이 점을 명시).
3. **`src/lib/progress.ts`**: `saveProgress`가 이제 upsert 시 `device_id`/
   `device_label`을 같이 보내고 `onConflict`도 `user_id,part,file_key,device_id`로
   바뀌어, 다른 기기의 행을 덮어쓰지 않는다. `loadProgress`(학습/시험/지문이 화면을
   열자마자 자동으로 이어받는 용도)는 의도적으로 **이 기기의 행만** 본다 — 자동으로
   다른 기기 진행을 가져오면 놀랄 수 있어서다. `listSavedProgress`(연습 파트
   "이어서 연습하기" 목록)는 반대로 **모든 기기의 행을 전부** 돌려주고, 각 항목에
   `deviceId`/`deviceLabel`/`isThisDevice`를 붙인다 — 같은 파일 조합이라도 기기가
   다르면 절대 하나로 합치지 않는다(요청하신 "일단 기록을 모두 유지"). `deleteProgress`
   에 `deviceId` 인자를 추가해 특정 기기의 행만 골라 지울 수 있게 했다.
4. **`src/lib/learningLog.ts`**: 같은 패턴을 `learning_log`에도 적용
   (`upsertLearningLog`/`listLearningLogs`/`listAllLearningLogs`/`deleteLearningLog`
   전부 device_id 인식). 로컬 병합 함수들(`mergeByFileKey` 등)도 병합 키를
   `fileKey`에서 `fileKey::deviceId`로 바꿔, 다른 기기의 기록이 병합 과정에서
   사라지지 않게 했다.
5. **UI**:
   - 설정 화면에 **"이 기기 이름"** 카드 신설(직접 이름 짓기, 기기 종류 추측값이
     기본으로 채워짐, 이 기기에만 저장).
   - 연습 화면 "이어서 연습하기" 카드, 설정 "학습 기록 관리" 목록, 연습/학습 화면
     맨 아래 "선택된 파일" 요약 패널(`SessionInfoPanel`)에 각 기록의 기기 이름 +
     "(이 기기)" 표시 + 날짜를 추가했다. `SessionInfoPanel`의 드롭다운도 같은
     파일 조합이 여러 기기에 있으면 전부 구분해서 보여준다.
   - 삭제 버튼들(연습 화면 카드, 학습 기록 관리)이 이제 정확히 "그 기기의 그
     기록"만 지운다 — 같은 파일 조합의 다른 기기 기록은 안 건드린다.
   - "이 학습 다시 하기"로 다른 기기의 기록을 선택하면, 그 기기의 정확한 파일
     조합을 그대로 불러와 이 기기의 새 기록으로 시작한다(중간 지점 자체를 정확히
     이어받을 수는 없다 — 몇 번째 단어까지 봤는지는 저장되지 않고 완료 개수
     요약만 남기 때문. 이 한계는 README에도 명시).

## 긴 파일명이 "..."으로 잘리던 것 → 가로 스크롤

`truncate`(말줄임표) 대신 `overflow-x-auto` + `whitespace-nowrap`으로 바꿔서
잘리지 않고 옆으로 밀어서 전부 볼 수 있게 했다. 적용한 곳: 연습 화면 "이어서
연습하기" 카드, 설정 "학습 기록 관리" 목록, `SessionInfoPanel`의 "선택된 파일"
줄, 파일 선택기(`FileSelector`)의 개별 파일명 줄.

## 검증

`tsc --noEmit`·`eslint src/` 통과. 로컬 dev 서버는 Supabase가 없어서 기기 간
실제 서버 동기화까지는 검증 못 했지만(코드 리뷰로 로직 검증), 로컬 저장소 경로는
크롬으로 실제 확인했다:

- 설정에서 "이 기기 이름"을 "내 맥북 테스트"로 저장 → localStorage에 정확히
  저장되는 것 확인.
- 연습을 시작해 바로 종료 → "이어서 연습하기" 카드에 "내 맥북 테스트 (이 기기) ·
  2026.09.08 09:14"가 표시되는 것 확인.
- 화면 맨 아래 "선택된 파일" 패널의 드롭다운에도 같은 기기 이름이 붙어 나오는 것,
  "기기" 항목이 새로 표시되는 것 확인.
- 드롭다운에서 그 조합을 골라 [이 학습 다시 하기]를 눌렀을 때 **처음부터 다시
  섞이지 않고** 정확히 그 지점(같은 단어, 같은 진행률)으로 이어지는 것 확인 —
  fileKey뿐 아니라 deviceId까지 맞춰서 "이 기기의 진행"과 정확히 매칭하는 로직이
  올바르게 동작함을 검증.
- 카드의 "삭제" 버튼으로 지우면 학습 기록 관리에서도 즉시 사라지는 것(기존 기능)
  이 deviceId 인자가 추가된 뒤에도 그대로 동작하는 것 확인.
- 테스트 데이터는 전부 지웠다.

## 사용자가 꼭 해야 하는 것 — Supabase에 스키마 재적용 필요

**이 기능이 실제 배포 환경에서 동작하려면, Supabase 프로젝트의 SQL Editor에서
`supabase/schema.sql` 파일 전체를 다시 붙여넣고 실행해야 한다.** `device_id`
컬럼과 새 기본키가 실제 데이터베이스에 없으면, 이 코드가 배포돼도 저장 시도가
전부 실패한다(다만 이 기기 로컬 저장은 계속 되므로 당장 이 기기에서 이어하기가
깨지지는 않는다 — 다른 기기와의 동기화만 안 될 뿐). 코드는 깃에 커밋해도
SQL은 자동으로 반영되지 않으므로, 이 부분은 반드시 사용자가 직접 Supabase
대시보드에서 실행해야 한다고 답변에 명확히 안내했다.

## 기존 학습 DB에 미치는 영향

**있음(의도된 것)**: 스키마의 기본키가 바뀐다(`add column`/`drop constraint`/
`add primary key` — 전부 `if not exists`/`if exists`라 안전하게 재실행 가능).
기존 행은 지워지지 않고 `device_id=''`로 그대로 남아 계속 보이고 계속 쓸 수
있다. 코드 쪽은 이 기본키 변경에 맞춰 upsert의 `onConflict` 대상을 함께 바꿨다
— 스키마와 코드를 항상 같이 배포해야 하며, SQL을 안 돌리고 코드만 배포하면
(또는 그 반대) 저장이 실패한다.

## 2. (같은 날, 이어서) "기기가 바뀌면 어디까지 했는지 이어지던 게 안 된다"

## 요청 사항

"기기가 바뀌더라도, 번호를 지정하면, 어느 단어까지 했는지 저장되는 구현이
이전에는 되었는데, 다시 구현해줘."

## 원인 — 위 1번 수정이 만든 진짜 회귀

1번에서 "기기별로 안 덮어쓰고 다 보존"하려고 `progress`/`learning_log`의
조회 함수에 전부 `device_id` 필터를 넣었는데, 그중 **`loadProgress`**(학습/
시험/지문 파트가 화면을 열자마자 자동으로 이어받는 함수)에도 실수로 "이 기기의
행만" 보도록 필터를 걸어버렸다. `device_id`가 생기기 전에는 (사용자, 파트,
파일 조합)당 행이 하나뿐이라 기기가 달라도 그 하나의 행을 그대로 이어받았는데,
이 필터 때문에 **새 기기에서 열면 그 기기 자신의 행이 없으니 그냥 처음부터
시작**하게 되어버렸다 — 정확히 사용자가 겪은 회귀였다.

## 수정

`loadProgress`에서 `device_id` 필터를 빼고, 그 대신 `order("updated_at",
{ascending:false}).limit(1)`로 **이 조합에서 기기 상관없이 가장 최근에 저장된
행 하나**를 가져오도록 고쳤다(기존엔 `.maybeSingle()`이었는데, 필터를 빼면
여러 기기의 행이 동시에 나올 수 있어 `.maybeSingle()`은 에러가 나므로
`order`+`limit(1)`로 바꿨다). 이 기기가 이어서 저장할 때는 여전히 이 기기의
`device_id`로 저장하므로(1번에서 이미 그렇게 되어 있었음), 원래 저장했던
기기의 기록은 덮어써지지 않고 "학습 기록 관리"에 별도로 남는다 — 즉 "기록은
기기별로 보존하되, 이어받을 때는 항상 최신 걸 자동으로 쓴다"로 두 요청을
동시에 만족시켰다.

같은 이유로 연습 화면의 "이 학습 다시 하기"(`SessionInfoPanel`의 `onRestore`
핸들러)에서도 `deviceId` 일치를 요구하던 조건을 없애고 `fileKey`만으로
매칭하도록 되돌렸다 — `savedList`가 이미 기기 상관없이 최신순으로 정렬돼
있어서 `.find()`가 자연히 가장 최근 기록을 고른다. 연습 파트의 기본 진입
버튼(`begin()`)은 애초에 `deviceId` 필터가 없어서 이번 회귀의 영향을 받은
적이 없었다(따로 확인만 함).

## 검증

`tsc --noEmit`·`eslint src/` 통과. 로컬(Supabase 미설정, localStorage 경로만
검증 가능)에서 학습 파트로 4번째 단어까지 넘긴 뒤 새로고침 → "저장된 학습
진행이 있습니다: ... · 3/70 — 이어서 학습하기"로 정확히 그 지점이 복원되는
것 확인(로컬 사본 경로가 이번 수정으로 안 깨졌음을 검증). 실제 기기 간
교차 동기화(다른 device_id의 행을 가져오는 것)는 로컬에 Supabase가 없어
직접 재현은 못 했고, 쿼리 구조(필터 제거 + `order`+`limit(1)`)를 코드로
재검토해 의도한 대로 최신 행을 가져옴을 확인했다.

## 기존 학습 DB에 미치는 영향

없음 — 조회 로직만 되돌린 것이라 저장 방식(스키마, `onConflict` 대상)은
1번에서 바뀐 그대로 유지된다. README의 관련 설명(1번에서 "다른 기기 기록은
처음부터 다시 시작"이라고 잘못 적었던 부분)도 실제 동작(정확한 지점 이어받기)
에 맞게 다시 고쳤다.
