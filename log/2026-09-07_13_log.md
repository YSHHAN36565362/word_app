# 2026-09-07 작업 로그

## 1. "학습 기록 관리"에서 지워도 "이어서 연습하기"에 그대로 남는 버그

## 요청 사항

"학습 기록 관리가 삭제는 되는데, 데이터 베이스 연동이 안되는지, 연습 모드
등에서는 삭제한 것이 그대로 나와. 그래서 다른거 보고 싶어도 칸 수 때문인지
짤려서 안보여." + "예를 들어, 나는 54개 학습 중인 것을 보고 싶은데, 이전에
학습 중인거 개수 제한 때문인지 저게 안떠. 잘 동기화 되게 해줘."

실제 화면(사용자가 붙여준 스크린샷): 설정의 "학습 기록 관리"에는 연습 파트
기록 2개("...Word_1-10.txt 외 7개" 3/1753개, "2026-08-13_...Word_1-10.txt
외 7개" 54/1658개)가 있는데, 연습 화면의 "이어서 연습하기"에는 4개가 뜨고
그중 "3/1753개" 조합만 겹치고 **"54/1658개" 조합은 아예 없음**.

## 원인 1 — "학습 기록 관리"의 삭제가 실제 이어하기 큐(progress)는 안 지움

`more/settings/page.tsx`의 `handleDeleteLog`는 `deleteLearningLog()`만
불렀다. 이 함수는 "학습 기록 관리" 목록을 채우는 `learning_log` 테이블(요약
정보: 완료 개수·최근 학습 시각)만 지우고, 연습 화면이 "이어서 연습하기"를
채우는 `progress` 테이블(실제 남은 큐)은 전혀 건드리지 않는다. 그래서 학습
기록에서 어떤 조합을 지워도, 연습 화면에는 그 조합의 진행 큐가 그대로 남아
"이어서 연습하기" 카드로 계속 나타난다 — 정확히 사용자가 겪은 증상("삭제한
것이 그대로 나와").

## 수정

`handleDeleteLog`가 연습 파트일 때는 `deleteLearningLog`와 함께
`deleteProgress(userId, "practice", entry.fileKey)`도 같이 호출하도록
고쳤다. 연습 파트는 파일 조합(`fileKey`)별로 독립된 진행 슬롯을 쓰기 때문에
`entry.fileKey`를 그대로 넘기면 정확히 같은 조합의 큐가 지워진다.

학습/시험/지문 파트는 일부러 그대로 뒀다 — 이 세 파트는 파트당 진행 슬롯이
하나뿐이라(`file_key=""`), "학습 기록 관리"에서 넘어온 파일 조합이 지금
그 슬롯에 저장된 진행과 실제로 같은 조합인지 구분할 방법이 없다(특히 시험·
지문은 진행 데이터에 실제 파일 경로 자체를 저장하지 않고 화면 표시용 이름만
저장함). 여기서 무조건 지우면, 학습 기록에서 지운 조합과 무관한 다른 진행
중인 세션을 실수로 날려버릴 위험이 있어 — 일단 확실히 안전한 연습 파트만
고쳤다. 삭제 확인 문구에도 연습 파트일 때만 "이어서 연습하기 카드에서도
사라집니다."를 추가해 실제 동작을 정확히 안내한다.

## 원인 2(가능성) — "이어서 하기" 목록의 서버 조회 상한이 너무 낮음(20개)

`progress.ts`의 `listSavedProgress`가 Supabase에서 가져오는 개수를
`updated_at` 최신순 **20개**로 제한하고 있었다(`learning_log` 쪽은 100개).
파일 조합을 자주 바꿔가며 공부하는 사람은 아직 안 끝낸 조합이 20개를 넘게
쌓일 수 있고, 그러면 오래전에 시작해 여전히 진행 중인 조합이 "최근 20개" 밖
으로 밀려나 "이어서 연습하기" 목록에서 통째로 안 보이게 된다 — "학습 기록
관리에는 있는데 이어서 하기엔 없다"는 이번 증상과 정확히 들어맞는 설명이라,
상한을 `learning_log`와 같은 **100개**로 올렸다.

**정직하게 밝혀둘 점**: 이 사용자의 실제 계정 데이터(Supabase)에는 직접
접근할 수 없어서, "54/1658개" 조합이 실제로 이 상한 때문에 빠졌던 것인지,
아니면 다른 이유(예: 그 조합의 progress 행이 실제로 이미 지워진 상태)였는지
100% 확답은 못 한다. 다만 상한을 올리는 것 자체는 안전하고 명백히 더 나은
방향이라 바로 반영했다.

## 검증

`tsc --noEmit`·`eslint src/` 통과. 로컬 dev 서버(Supabase 미설정, localStorage
경로만 검증 가능)에서 크롬으로:

1. 테스트 번호로 연습을 시작 → 헷갈림 채점 1회 → "연습 종료하기"로 나감.
2. 새로고침 후 설정 "학습 기록 관리"와 연습 화면 "이어서 연습하기" 양쪽에
   그 조합이 정상적으로 뜨는 것 확인.
3. `window.confirm`을 자동 승인하도록 임시로 바꿔둔 뒤(크롬 자동화 중
   네이티브 confirm 다이얼로그가 CDP 입력을 막아버려서 우회) "학습 기록
   관리"에서 삭제 → 그 즉시 "학습 기록 관리"에서 사라지는 것 확인.
4. 연습 화면으로 이동 → "이어서 연습하기"가 "저장된 데이터가 없습니다."로
   바뀐 것 확인(수정 전이었다면 계속 남아있었을 카드).
5. 테스트로 만든 번호·데이터는 확인 후 전부 지웠다.

## 기존 학습 DB에 미치는 영향

이번 수정은 "삭제" 동작 범위를 원래 사용자가 기대한 대로(연습 기록 삭제 =
이어하기 큐도 같이 삭제) 넓힌 것과, 조회 상한을 올린 것뿐이다. 기존에 저장된
데이터를 읽거나 쓰는 방식 자체는 바뀌지 않았고, 앞으로 "학습 기록 관리"에서
연습 조합을 지우면 그 조합의 "이어서 연습하기" 카드도 함께 사라진다는 점만
사용자에게 안내가 필요하다(의도된 동작 변경).

## 2. (같은 요청, 별개 사안) 폰-노트북 간 동기화가 안 되는 것 같다는 제보

## 요청 사항

"컴퓨터와 휴대폰의 번호가 같은데도 저장이 안되는 거같아. 휴대폰은 9/6일
학습했는데, 노트북에는 없어. 같은 번호로 학습했는데도. 내 번호 저장을
눌러서 또 업데이트를 해야되는건가?"

## 코드 검토 결과

- "내 번호 저장" 버튼은 번호를 **새로 설정/변경**할 때만 쓰는 버튼이고, 이미
  설정된 번호로 계속 쓰는 동안에는 다시 누를 필요가 없다 — 학습 중 채점·진행
  저장은 `saveProgress`/`upsertLearningLog`가 단어를 넘길 때마다 자동으로
  호출한다(코드상 확인).
- `sanitizeUserId`가 저장 시 공백·특수문자를 제거하므로 "77 "과 "77"처럼
  기기별로 오타/공백이 달라 다른 사용자로 갈리는 경우는 코드상 배제된다.
- `listAllLearningLogs`/`listSavedProgress`는 캐시 없이 페이지를 열 때마다
  Supabase에서 새로 조회한다(서비스 워커/PWA 캐시도 이 프로젝트엔 없음 —
  `public/manifest.json`만 있고 실제 캐싱 로직은 없음을 확인). 즉 코드 구조상

## 이번에 확인하지 못한 것 (한계)

이 사용자의 실제 배포 환경·Supabase 프로젝트에는 접근 권한이 없어서, 실제로
폰에서의 저장이 서버까지 도달했는지, 노트북 조회가 정확히 같은 프로젝트/
테이블을 보는지는 로그 파일이나 이 세션에서 직접 확인할 방법이 없다. 대신
아래 순서로 사용자가 직접 확인해볼 것을 답변에서 안내했다:

1. 노트북에서 이미 열려있던 탭이 아니라 **완전히 새로고침**(또는 새 탭)한
   상태에서도 안 보이는지 (열어둔 탭은 그 자리에서 다시 안 불러온다).
2. 폰과 노트북이 정확히 **같은 주소(도메인)**를 쓰는지(다른 배포 URL·미리보기

3. 폰에서 학습 직후 F12(또는 원격 디버깅)로 콘솔에 `[Supabase] ... 실패` 로그가
   찍혔는지 — 이 앱은 Supabase 저장 실패 시 이 형식으로 콘솔에 남기게
   되어 있다(이전 세션에 추가한 `logSupabaseError`).

코드 자체에서 발견되는 명백한 버그는 없었으므로, 위 확인 후에도 재현되면
그때 더 구체적인 정보(에러 로그, 두 기기의 실제 접속 주소)를 갖고 다시
봐야 한다고 답변에 명시했다.

## 3. (같은 날, 이어서) 후속 요청 4건 — 학습 기록 로딩 멈춤 버그, 연습 화면
   자체 삭제, 발음 듣기 버튼 크게 + S 단축키

## 요청 사항

"여전히, 설정의 내 번호에서 보는 단어 학습 기록과 연습 모드 등에서의 데이터
베이스 저장이 다른거 같은데 확인해줘. 그리고 연습 모드 등 시작 페이지에서도
학습 기록이 삭제 가능하도록 해줘. 0개 학습 중인게 너무 많다. 그리고 소리 듣기
버튼을 좀 크게 해주고, 단축키를 영어로 S로 해주고, 연습 모드 등에서도 단축키가
보이게 해줘."

사용자가 붙여준 새 스크린샷: 설정의 "학습 기록 관리"가 **"불러오는 중..."에서
멈춰 있고**(로딩이 안 끝남), 연습 화면의 "이어서 연습하기"는 4개가 정상적으로
뜬 상태 — "학습 기록과 저장이 다른 것 같다"는 게 실제로는 데이터가 다른 게
아니라, 설정 페이지의 조회 하나가 멈춰 있는 것으로 확인됐다.

## 1. "학습 기록 관리" 로딩이 영원히 안 끝나는 버그 — 원인 발견·수정

`more/settings/page.tsx`의 `listAllLearningLogs(userId).then(...)`에
`.catch()`가 없었다. 이 요청이 실패(reject)하면 `.then()` 콜백 자체가 안
불려서 `setLogsLoading(false)`가 영원히 안 불리고, 화면은 "불러오는 중..."에
그대로 멈춰버린다 — 정확히 사용자가 겪은 증상. `.catch()`를 추가해 실패해도
로딩을 끝내고, "학습 기록을 불러오지 못했어요" 안내 + "다시 시도" 버튼을
보여주도록 고쳤다(재사용 가능하게 `loadLogs()` 함수로 분리, 버튼이 같은
함수를 다시 부름).

## 2. 연습 모드 시작 화면에서 "이어서 연습하기" 카드 자체 삭제

"0개 학습 중인게 너무 많다"는 요청대로, 설정까지 안 가고 연습 화면
"이어서 연습하기" 카드에서 바로 지울 수 있는 "삭제" 버튼을 추가했다
(`deleteSavedEntry`). 오늘 앞서 고친 것과 같은 이유로 `progress`·
`learning_log` 둘 다 같이 지운다(한쪽만 지우면 다른 목록에 다시 나타나므로).

## 3·4. 발음 듣기 버튼 확대 + S 단축키 + 단축키 표시

- `SpeakButton`의 `compact`(원형 아이콘) 크기를 24px→36px, 아이콘
  16px→22px로 키웠다.
- `speak()` 함수를 `SpeakButton.tsx`에서 내보내(export) 페이지에서 버튼
  클릭을 흉내내지 않고 바로 부를 수 있게 했다.
- **학습 화면**: 기존에 `s` 단축키가 전혀 없어서 그냥 `speak(현재 단어)`로
  바로 연결했다(한글 자판 등에서 `e.key`가 안 잡히는 경우를 대비해 `KeyH`
  패턴과 같은 이유로 `KeyS`도 같이 등록).
- **연습 화면**: `s`가 이미 WASD 채점 배치의 "모름"(↓ 방향)이라 그대로 겹치면
  안 된다. 그런데 기존 코드가 `s: () => { if (showAnswer) score(0); }`라
  **정답을 열기 전에는 원래 아무 동작도 안 하고 있었다** — 그 죽어있던 구간을
  발음 듣기로 채웠다: `showAnswer`가 true면 그대로 모름 채점, false면 발음을
  들려준다. 기존 채점 동작은 전혀 안 바뀌고 사각지대만 활용한 것이라 충돌이
  없다.
- 학습·연습 화면 둘 다 스피커 버튼 옆에 `<KeyBadge>S</KeyBadge>`("[S]")를
  붙이고, 화면 상단 "단축키:" 안내 문구에도 각각 반영했다(연습 화면은
  "S(답 열기 전)=발음 듣기"로 명시해 채점용 S와 헷갈리지 않게 함).
- README(한국어·일본어) "발음 듣기"/"학습 기록 관리" 설명도 이번에 바뀐
  동작에 맞게 갱신했다.

## 검증

`tsc --noEmit`·`eslint src/` 통과. 크롬으로:

- 학습 화면에서 스피커 버튼이 눈에 띄게 커진 것 확인, `S` 키를 눌러도 콘솔
  에러 없는 것 확인.
- 연습 화면에서 정답 열기 전 `S`를 눌러도 카드가 안 넘어가는 것(발음만 재생,
  채점 안 됨) 확인 → 정답 공개 후 `S`를 누르니 빨간 플래시와 함께 모름으로
  채점되고 다음 카드로 넘어가는 것 확인(기존 동작 그대로 유지).
- 테스트 세션으로 "이어서 연습하기" 카드를 하나 만든 뒤 새로 생긴 "삭제"
  버튼을 눌러(자동화 중 window.confirm이 CDP 입력을 막아 `window.confirm =
  () => true`로 임시 우회) 그 자리에서 바로 사라지는 것, 설정의 "학습 기록
  관리"에서도 함께 사라진 것("저장된 학습 기록이 없습니다.") 확인.
- 테스트로 만든 번호·데이터는 확인 후 전부 지웠다.

## 기존 학습 DB에 미치는 영향

로딩 실패 처리 추가, 삭제 버튼 위치 추가, 단축키 추가는 전부 프론트엔드
로직이다. `deleteSavedEntry`가 호출하는 `deleteProgress`/`deleteLearningLog`
는 이미 있던 함수 그대로이고, 사용자가 명시적으로 "삭제"를 누를 때만
동작한다. 새 테이블·컬럼·쿼리 없음.
